# Vision and Approach

This page explains why TodoHeap exists, what it is trying to solve, and where the product is heading. For code structure see the [Developer Guide](./index.md).

## The problem

Students juggle many parallel tasks with different deadlines: coursework, competitions, papers, student clubs. Task lists solve **forgetting** but not **procrastination**.

A list answers two questions — what to do and when it is due — but not the questions that actually drive execution:

- When should I start?
- Which step comes first?
- How long does each step take, and which time slot should it occupy?

In short, a list does not turn a vague **task** into a precise **schedule**. Once the pressure of an unstructured backlog overloads the emotional system, people procrastinate; a growing pile of open tasks is itself a persistent mental burden.

Turning vague tasks into schedules is exactly the kind of planning work that could not be mechanized before LLMs and agents. That is where TodoHeap comes in.

## Who it is for

The primary audience is **university students with highly parallel coursework and affairs** (upper-year undergraduates and graduate students), especially during exam weeks, competition seasons and thesis periods. They have many small tasks, dense deadlines and uneven scheduling skills.

The same need extends naturally to knowledge workers with similar workloads.

## Product goal

**Turn vague tasks into executable, trackable and adjustable schedules.** The agent handles understanding, decomposition, scheduling, verification and adjustment; the user confirms and executes.

The loop:

```
Task input → Agent planning → Calendar commit → Execution feedback → Auto-adjustment
```

| Stage | What it should do | Current state |
| --- | --- | --- |
| Understand | Capture task content, deadlines and missing information; ask follow-up questions | Natural-language input and AI analysis exist; multi-turn clarification is not implemented |
| Plan | Break work into dependent subtasks, estimate effort, build a task graph | Multi-parent task graph and effort field exist; AI decomposition creates subtasks, estimates still come from the model |
| Schedule | Combine existing events and free time to produce candidate schedules under deadline, dependency and daily-capacity constraints | The schedule view lays unfinished tasks out by deadline; constraint solving is not implemented |
| Verify | Check time conflicts, dependency order, deadlines and daily workload | No standalone verification stage yet |
| Commit | Write confirmed plans into the calendar, support ICS export and third-party sync | The `schedules` table and RLS exist; write path and ICS export are not implemented |
| Feedback | Track completion rates and estimate drift, re-plan locally when execution slips | No long-term memory or automatic re-planning yet |

::: tip Documentation scope
The table maps the product goal; it is not a list of shipped features. The user guide only describes capabilities available today.
:::

## Agent architecture

The approach uses **Planner–Executor–Reviewer** collaboration:

| Role | Responsibility |
| --- | --- |
| Planner | Understand intent, ask clarifying questions, decompose tasks, estimate effort, propose schedules |
| Executor | Call tools for calendar queries, schedule solving, plan commits, status write-back and memory |
| Reviewer | Verify conflicts, dependencies, deadlines and daily workload; trigger retries or local re-planning |

A lightweight state machine drives the flow through `clarify`, `decompose`, `estimate`, `schedule`, `verify`, `commit` and `reflect`. Each step emits structured events so the UI can show what the agent is doing.

Memory is split into:

- **Short-term**: current session, task tree, candidate plans, unconfirmed edits.
- **Long-term**: preferred working hours, historical estimate drift, completion rates and common delay reasons.

## Scenarios

- **Large task decomposition**: "Finish the course paper in two weeks" becomes topic selection, literature search, outline, draft, revision and formatting, with dependencies and suggested order.
- **Inbox triage**: A pile of captured todos ("lab report due Wednesday, buy materials, book a slot with the professor") is grouped, decomposed and scheduled.
- **Long-horizon planning**: Exam preparation or a thesis spans weeks; remaining time and daily capacity are spread across future days.

## How it differs

TickTick and similar tools expose MCP interfaces for CRUD on **tasks**, not schedules. Conversational agents can suggest a plan once, but they cannot see the user's free calendar time, write the plan into a calendar, or adjust it when execution drifts.

TodoHeap is not another smarter list. It turns the planning work between "task" and "schedule" into a visible, confirmable collaboration.

## Design principles

- **The user has the final say**: the agent proposes, the user confirms before anything is written to the calendar.
- **Visible process**: decomposition, scheduling and verification surface as structured events, not a black box.
- **Reversible writes**: optimistic updates and rollback apply to every write path.
- **Capabilities land in layers**: make task trees and priority reliable first, then add scheduling, verification and memory.
