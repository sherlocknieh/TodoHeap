# 项目愿景与方案

这一页说明 TodoHeap 为什么存在、要解决什么问题，以及产品最终要走到哪里。具体的代码结构见[架构与技术栈](./02.architecture.md)。

## 要解决的问题

大学生日常面对大量并行、截止日期各不相同的任务：课程作业、竞赛、论文、社团事务。为了不遗忘，绝大多数人会用任务清单记录待办。

但长期使用下来可以确认一个事实：**任务清单能解决"记不住"，却解决不了"拖延"**。

清单只回答了两个问题——"要做什么"和"最晚什么时候交"，却没有回答真正决定执行的几个问题：

- 什么时候开始做？
- 先做哪一步、后做哪一步？
- 每一步大概要多久、放在哪个时间段做？

总结起来就是：没能把模糊的**任务**变成精确的**日程**。当任务压力让情绪系统过载时，人就会拖延；长期停留在"待办"状态的任务堆积，本身也构成持续的悬而未决感。

把模糊任务精确化为日程，是一个无法被机械化的复杂过程。大模型与 Agent 让这个过程第一次有了自动化的可能，这正是 TodoHeap 的切入点。

## 目标人群

核心用户是**课业与事务高度并行的大学生**（本科高年级与研究生为主），典型时段如考试周、竞赛季、论文季：任务杂、截止日期密集、自主安排时间的能力参差不齐，最需要"帮忙把事排进日程"的工具。

后续可自然扩展到具有类似特征的知识工作者。

## 产品目标

**把模糊的任务精确化为可执行、可追踪、可调整的日程**，由 Agent 完成理解、拆解、排程、校验与调整，用户只负责确认与执行。

整体闭环：

```
任务输入 → Agent 规划 → 日历落地 → 执行反馈 → 自动调整
```

| 环节 | 要做的事 | 当前状态 |
| --- | --- | --- |
| 感知与澄清 | 识别任务内容、截止时间与缺失信息，必要时追问 | 由对话 Agent 承担自然语言理解与追问 |
| 任务规划 | 拆成有依赖关系的子任务，估算工时，形成任务图 | 已支持多父任务图与工时字段；Agent 可生成子任务，估时仍由模型建议 |
| 智能排程 | 结合已有日程与可用时间，在截止日期、依赖与每日上限约束下生成候选排程 | 日程视图按日期展示已导入的事件；约束求解尚未实现 |
| 校验 | 检查时间冲突、依赖顺序、截止日期与每日工作量 | 未实现独立的校验环节 |
| 确认与执行 | 用户确认后写入日历，可导出 ICS；可接入第三方服务 | 已支持 `schedules` 的 ICS 导入导出与只读订阅链接；写入由用户订阅完成 |
| 反馈与调整 | 记录完成率与估时偏差，执行偏离后局部重排 | 未实现长期记忆与自动重排 |

::: tip 文档口径
上表是产品目标的对照，不是已发布功能的清单。用户指南只描述当前可用的能力；标记为"规划中"的部分请勿当作现有功能使用。
:::

## Agent 架构

方案采用 **Planner–Executor–Reviewer** 三角色协作：

| 角色 | 职责 |
| --- | --- |
| Planner | 理解意图、提出澄清问题、拆解任务、估时、生成排程方案 |
| Executor | 调用日历查询、排程求解、计划写入、状态回写与记忆读写等工具 |
| Reviewer | 校验时间冲突、依赖关系、截止日期与每日工作量，发现问题时触发重试或局部重排 |

流程由轻量状态机管理，主要状态为 `clarify`、`decompose`、`estimate`、`schedule`、`verify`、`commit`、`reflect`。每一步都产生结构化运行事件，便于在界面上实时展示 Agent 正在做什么。

记忆分两类：

- **短期记忆**：当前会话、任务树、候选方案与尚未确认的修改。
- **长期记忆**：用户偏好的工作时段、历史估时偏差、完成率与常见延期原因。

## 典型场景

- **大任务分解**：如"两周内完成课程论文"，自动拆成选题、检索文献、列提纲、写初稿、修改、排版等子任务，并给出依赖关系与建议顺序。
- **任务自动整理**：用户一次性丢进一堆待办（"周三交实验报告、买资料、约老师答疑"），系统归类整理、拆解子任务并生成日程。
- **长期任务安排**：考研复习、毕业设计等跨周任务，按剩余时间与每日可投入时长分摊到未来日程，避免前松后紧。

## 与现有产品的差异

滴答清单等工具已经提供 MCP 接口供 Agent 增删改查，但操作对象仍是"任务"；通用对话式 Agent 能给出一次性排程建议，却感知不到用户日历的空闲时间，也不会把建议落进日历、在偏离后自动调整。

TodoHeap 的目标不是再做一个更聪明的清单，而是把"任务 → 日程"这段原本靠人脑完成的规划工作，变成可视化、可确认的协作流程。

## 设计原则

- **用户保有最终确认权**：Agent 产出候选方案，写入日历前由用户确认。
- **过程可见**：拆解、排程与校验都以结构化事件呈现，而不是黑箱结果。
- **可回退**：所有写操作沿用乐观更新与回滚机制，失败不留下半成品数据。
- **能力分层落地**：先保证任务树与优先级可靠，再逐步补齐排程求解、校验与记忆。
